<objective>
Implement `POST /api/ingest/batch` end-to-end (D-30 through D-37): auth-before-validate, all-or-nothing
array validation, ascending sort + JS-level pre-dedup, a single bulk upsert-ignore-duplicates call,
sequential scoring of newly-inserted rows, and the D-27/D-28 backfill-rescore pass over the
`[batch_min, batch_max + 12h]` window. Then harden it against the cap/all-or-nothing/duplicate/dedup-fidelity
edge matrix.

Purpose: This is the actual product feature (ING-03) the phase exists to deliver — buffered offline
readings arrive as a batch, land under their true original timestamps, and are risk-scored (including
retroactive correction of already-scored readings) exactly as if they had arrived live.
Output: `src/app/api/ingest/batch/route.ts`, extended `src/lib/validation/ingest-schema.ts` and
`src/lib/risk/compute.ts`, and `tests/ingest.batch.test.ts` proving every locked decision and edge case.
</objective>

<flagged_assumptions>
## Flagged Assumptions (surfaced per specless-probe-fallback — not silently resolved)

- **Concurrency:** Concurrent overlapping batch-sync or live-ingest requests for the same device
  are not explicitly serialized in this phase (no advisory lock, no per-device request queue).
  CONTEXT.md's decisions do not address this. Accepted as a residual risk for v1's single-device
  demo scope (PROJECT.md: no concurrent multi-caller access pattern expected); the DB-level unique
  constraint (D-33, Plan 03-01) still prevents duplicate-row corruption even if two overlapping
  requests race. Full concurrency safety (e.g. row locking during backfill-rescore) is deferred as
  a v2 concern if a real multi-caller deployment emerges.
- **Unbounded backfill blast radius from unvalidated timestamps:** Per D-28's explicit rationale
  (uncapped rescoring chosen "for correctness over defensive throttling" at v1 demo scale), no
  timestamp-range validation is added to `IngestSchema`/`BatchIngestSchema` in this phase. A batch
  with a crafted extreme-past timestamp could inflate `fetchWindow(deviceId, batchMin, batchMax +
  TREND_WINDOW_MS)`'s row count beyond the "few hundred rows" assumption CONTEXT.md reasoned from.
  This is an accepted residual risk (RESEARCH.md Open Question 1 / Pitfall 3), not silently
  resolved either way — revisit only if a real deployment shows pathological batch/timestamp
  values.
</flagged_assumptions>
