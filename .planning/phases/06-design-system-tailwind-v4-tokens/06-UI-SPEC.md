# Phase 6 — UI Design Contract (REWORK — supersedes the 2026-09-26 version)

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Why this file was regenerated

All 5 plans of the original Phase 6 executed against a narrow 4-component UI-SPEC (Button/Card/
Badge/Input only) and the user rejected the result wholesale — "everything looks so
[expletive] horrible... the only thing that is correct is the colours." `06-CONTEXT.md` was then
rewritten with D-12 through D-16, substantially expanding scope: a much larger component
inventory tied to real Figma node IDs, a first-class "shadcn-quality" docs site, a Home-dashboard
proof-of-concept page, and a mandatory Figma-extraction-then-screenshot-diff verification
mechanism. This file replaces the 2026-09-26 version in place. **D-01–D-05 (Tailwind install
location, palette origin, font) are locked and unchanged — do not re-derive colors or fonts.**
D-06/D-07/D-09 (strict typed variants, shadcn+Radix base, custom icon set) are also unchanged in
principle; only D-08's *inventory* is superseded by D-12.

## Typography

**This expands the prior 4-role scale to 7 roles + a 3rd weight — this is a deliberate,
justified expansion, not scope creep.** The prior UI-SPEC intentionally trimmed to 4 roles
because Phase 6 only exercised 4 atomic components; D-12 now brings in a hero status headline,
a page title, and large tabular vital-metric numbers that those 4 roles cannot express. The
values below are **not invented** — they are the project's own already-authored canonical type
scale (`frontend-design/design-system/DESIGN-SYSTEM.md` §4, cited in `06-CONTEXT.md`'s
`<canonical_refs>` as "still the strict-rule source of truth"), just adopted now that scope
needs them. Two of the "new" roles below add no new size at all — they reuse an existing size at
a different weight (the same recombination pattern the old spec already used for `Button`'s
label).

| Role | Size | Weight | Line Height | Status |
|------|------|--------|-------------|--------|
| Display (hero headline, e.g. "Baby is Resting Safely") | 38px (`2.375rem`) | **700 bold (NEW)** | 1.15 | New size + new weight |
| Heading — page title | 24px (`1.5rem`) | 700 bold | 1.30 | New size, reuses new weight |
| Heading — section (existing `--text-heading`, unchanged token) | 18px (`1.125rem`) | 600 semibold | 1.3 | Unchanged |
| Heading — card (vital-card label, e.g. "Pulse") | 16px | 600 semibold | 1.40 | **Recombination** — Body's size + Heading's weight, no new token needed beyond a line-height variant |
| Body (default text, `Input`/`Field` value) | 16px (`1rem`) | 400 regular | 1.5 | Unchanged |
| Label (`Badge`/`Field` label) | 13px (`0.8125rem`) | 600 semibold | 1.4 | Unchanged |
| Secondary text (timestamps, telemetry sub-labels) | 13px | 400 regular | 1.45 | **Recombination** — Label's size at Body's weight |
| Caption (helper text, error text, units) | 12px (`0.75rem`) | 400 regular | 1.4 | Unchanged |
| Vital metric (large Pulse/Temp/Activity readings) | 36px (`2.25rem`) | 700 bold | 1.10 | New size, reuses new weight. **Must** use `font-variant-numeric: tabular-nums` (per `emil-ui-polish`) so the digits don't jiggle as readings update |

Weights, now exactly **3** total (was 2 — this is the one deliberate exception, mirroring how
spacing already carries a documented 12px exception): **400 regular**, **600 semibold**, **700
bold — reserved exclusively for Display, page-title Heading, and Vital-metric roles.** Never use
700 anywhere else; if a component seems to need "extra emphasis" outside those three roles, reach
for 600 + color, not 700 (per `emil-ui-polish` principle 2 — never change weight to signal
interaction state).

Font: Inter, unchanged (D-05).

```css
/* New/changed tokens only — existing --text-heading/--text-body/--text-label/--text-caption
   in globals.css are untouched */
--text-display: 2.375rem;
--text-display--line-height: 1.15;
--text-heading-page: 1.5rem;
--text-heading-page--line-height: 1.3;
--text-vital-metric: 2.25rem;
--text-vital-metric--line-height: 1.1;
/* "Heading — card" and "Secondary text" are recombinations — no new --text-* size token,
   just a different font-weight utility paired with an existing size token at the usage site. */
```

Also apply project-wide (per `emil-ui-polish`, not previously called out): real typographic
characters (curly quotes, `…` not `...`), `text-wrap: balance` on Display/page-title headings,
and `-webkit-font-smoothing: antialiased` (already present on `body` in `globals.css`).

### Flagged tension — "red-accented bottom nav" vs D-04

`06-CONTEXT.md`'s `<specifics>` section describes the user's target screenshot as having a
"red-accented bottom nav." D-04 locks pink/critical strictly to health-status semantics, never
decoration or navigation state. **Do not silently resolve this by using critical-pink as the
`NavBar` active-tab color** — that would violate a locked decision on a guess. Two real
possibilities: (a) the accent the user is describing is actually the brand blue reading warmer
in a photo/screenshot than it does in code, or (b) Figma's actual `279-320`/`279-758` node really
does use a red/pink tab-active state, which would be a genuine conflict the user needs to
resolve, not an implementation detail. Extract the real value from the Figma node screenshot
(D-15) first; if it does turn out to be a critical-pink hue, stop and surface this as a
`REVISION_CONFLICT`-style flag rather than building it — do not implement a decorative use of the

**Radius:**

| Token | Value | Usage |

**Shadow** (unchanged): `--shadow-card`, `--shadow-floating`, `--shadow-critical`,
`--shadow-focus` — all carry forward as-is from `globals.css`.

**Motion** (unchanged durations, now with explicit interaction rules per `emil-animations` /
`emil-ui-polish`, per D-13's mandate to invoke those skills):

| Token | Value | Usage |
|-------|-------|-------|
| `--duration-fast` | 150ms | Hover/press micro-feedback |
| `--duration-normal` | 250ms | Default transitions (focus ring, color change) |
| `--duration-slow` | 350ms | Loading skeleton pulse, spinner rotation |

Concrete rules for every new interactive component in this phase:
- **Press feedback:** `active:scale-[0.96]` with a `150ms ease-out` transition on `transform` —
  never below `0.96`. Apply to `Button`, `NavLink`, `ToggleGroup` items, `Switch`, `Checkbox`.
- **Hover:** transition only `color`/`background-color`/`box-shadow`, never `transition-all`,
  `150ms ease-out`. No font-weight change on hover (signal state with color only, per
  `emil-ui-polish` #2) — this directly affects `NavLink`'s active/inactive treatment.
- **Focus:** keep the existing neutral/brand focus ring (`--shadow-focus`); never recolor it per
  component to something clashing.
- Respect `prefers-reduced-motion` on every animation added — no exceptions, including the
  `Sparkline`/`Chart` entrance and the docs-site interactions below.
- Docs-site preview toggles (variant pickers, tabs) get `initial={false}` treatment — they are
  state changes, not first-run entrances; don't animate the doc page's own load per
  `emil-animations` principle 8.

## Docs Site Interaction Contract (D-13)

The current docs page (`src/app/design-system/docs/page.tsx`) was rejected as "a single page
bunch of crap" — one long scrolling page with static previews. The rebuild is a first-class
deliverable held to "shadcn-quality or better." Locked requirements:

1. **Navigation shell** — a persistent left sidebar (component list grouped by category:
   Actions, Forms, Cards, Navigation, Feedback/Status, Data Viz) + a main content pane, replacing
   the current single-scroll anchor-nav page. This is a structural change, not a styling pass.
2. **Per-component page**, each with:
   - A **live, interactive preview** — actual rendered variants/states the visitor can toggle
     (e.g. a variant picker for `Button`, a status picker for `Badge`), not static screenshots.
   - **Color and type reference** — which semantic tokens this component consumes, rendered as
     real swatches/type samples, not just named in prose.
   - **Usage + implementation notes** — when to use it, which variant applies where, one correct
     and one incorrect example (mirrors the existing `*.DESIGN.md` correct/incorrect pattern —
     surface that content in the UI, don't just link to a raw `.md` file dump like the current
     page does).
3. **Visual bar:** every one of the above uses this phase's own token set with intention — the
   docs site is itself proof the design system works, not a bare-bones internal tool.
4. **Micro-interactions** (per `emil-animations`/`emil-ui-polish`, invoked directly per D-13):
   variant pickers/tabs use the press/hover rules above; sidebar active-link state signals via
   color, never font-weight; no entrance animation on the docs page's own load.
5. This is guidance for the **researcher and planner** — D-13 explicitly does not ask for the
   docs site to be built during discussion, and this UI-SPEC does not build it either; the plan
   consuming this file does.
